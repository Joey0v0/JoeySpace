# JoeySpace 前端 F3 真实聊天设计（待审查，2026-10-09）

## 1. 目标与基线

从 F2 提交 `37c72cd` 出发，让桌面浏览器中的团队群和私聊能够读取、发送、恢复消息，并显式确认已加载消息。保留已确认的三栏布局、真实身份与会话导航。F3 的第一批重点是可用的讨论链路；默认总览需要权威未读数据，普通成员 `@我` 需要额外服务端契约，不能用 F1 样例或正文猜测冒充。

已核对：IM/Gateway 具备按单个群或私聊读取历史、未读计数、逐条已读的接口；IM 有离线读取与 ACK；F2 有团队群和持久私聊目录。WS 有单聊/群聊发送和 `msg_id` ACK，浏览器消息 ID 已作为十进制字符串。现有 WS 握手从 `?token=` 取 JWT，Origin 检查一律放行；当前 Vite 仅代理 `/api`。会话目录未包含跨类型未读、预览或 `@我`。这些事实以当前 F2 工作树代码为准。

## 2. 第一批可运行体验

1. 选定有权访问的群或私聊，读取最新历史并按持久消息 ID 加载更早记录。切换会话、身份或权限时旧回包不能进入新会话。渲染纯文本、发送者/机器人身份和时间；暂不把任务卡扩成完整交互。
2. 当前会话显示权威未读数，提供“将已加载的收到消息标为已读”。只提交本次已加载、属于当前会话且符合 IM 规则的持久 ID，每次最多 100 个。打开、滚动、实时接收、离线 ACK 都不自动已读。
3. 同源 WS 在线时发送纯文本；Enter 发送、Shift+Enter 换行、输入法组合期间不发送。按 `msg_id` 跟踪“发送中→已受理→历史已确认”，断线、超时或 ACK 丢失显示“结果待核对”，先查历史再允许同 ID 重试。ACK 只代表 Kafka 受理，不表示持久化或已读。
4. 实时帧与离线补拉按 `msg_id` 去重，持久历史按 `id` 分页。重连后重新读取当前会话最新页和未读；离线 ACK 只在消息已经安全进入当前身份的缓存后发送。离线接口目前不分页，大量积压时不能声称已完整补拉，需在实现中设防护并单独提出后端分页契约。
5. 正在看旧消息时新消息不强制滚到底部，提供“有新消息”；离开当前会话保留本标签页草稿，登出清空。发送失败不能清空草稿。

第一批仍可从 F2 的真实目录进入会话。默认 `/messages` 在聚合读契约完成前继续展示真实导航和明确的“未读总览待接入”，不能显示样例未读或空状态“全部已读”。

## 3. 需确认的契约与方案

### F09：浏览器 WS 认证与来源控制

**推荐 A：**保留现有 Bearer 身份模型，新增同源 HTTP 短时、一次性 WS 连接票据。HTTP 请求带 Authorization，经当前登录身份核验后得到随机票据；浏览器以 `wss://同源/ws?ticket=...` 握手，WS 原子消费票据并绑定身份/原 Token 的服务端短期记录，后续群发送仍由服务端带原身份复核。票据过期或重用拒绝；只允许配置的站点 Origin。旧 `/ws?token=` 入口在迁移期保留给演示页，限制来源并清理日志/代理中敏感查询串，随后单独废弃。Vite 为 `/ws` 配 WS 代理，生产静态页与 WS 同域路由在 F6 验收。

备选 B：正式页面继续使用 `?token=`，改动少，但长寿 JWT 会进入 URL、反向代理访问记录和诊断信息，Origin 全放行还增加跨站建立连接的机会。备选 C：改 HttpOnly Cookie，能避开 JS 可读 Token，但会改变 F2 的认证模型及 API/WS CSRF 策略。推荐 A 复用现有 Redis，代价是新 HTTP 握手入口、短期票据记录与过期/单次消费测试；具体票据有效期和错误映射实施契约时固定。任何方案均需维护现有群发送的实时资格复核。

### F10：跨会话未读总览

**推荐 A：**由 IM 提供本人可读的、按持久消息快照分页的群/私聊未读会话摘要。IM 计算各会话未读数、最新持久消息 ID、有限预览与游标；群只含当前已加入且有资格阅读的范围，私聊沿既有个人会话边界。Gateway 仅按 User 已有安全显示名接口补名称，不让前端逐个群发 N 次未读请求。首批可先做每会话权威未读计数；跨类型稳定分页和预览由同一 F3 契约后续子步交付，未完成前总览明确标注范围。

备选 B：前端遍历已加载目录并逐个调用现有计数，能更快显示局部数字，却会漏未加载会话、产生 N+1 请求，无法正确说“全部未读”。备选 C：新建持久聚合投影表，读性能更稳定，但额外写入/修复/迁移负担大，需真实性能证据。A 保持数据归 IM，代价是复杂的混合分页与群资格过滤；若真实 MySQL 执行计划证明需要索引，先单独审查迁移。

### F11：普通成员 `@我`

**推荐 A：**普通群聊消息另附结构化被提及成员 ID，由 IM 在接收时核验这些 ID 属于当前团队/群可提及成员，持久消息与提及关系同一写入链；`@我` 查询只依已验证关系与当前可读资格，且只显示未读提及。旧消息没有结构化关系时不回填猜测，`@AI 整理任务` 原有触发规则保持独立。普通用户正文中的名字不自动产生提及。

备选 B：解析正文 `@昵称`，无需发送协议变化，但重名、改名、复制文本与非成员提及都会误判。备选 C：F3 不提供 `@我` 筛选，工作量较低，但削弱用户先看讨论的主要路径。A 需要兼容的 WS/消息事件扩展、IM 存储与查询、成员选择 UI，可能需要迁移；在本人明确确认前不修改这些协议/表。第一批按上述真实聊天链路交付时，`@我` 明确显示“待接入”。

## 4. 安全与恢复约束

- 页面不渲染任意 HTML；消息、Token 和票据不写入日志。所有 HTTP/WS 的大 ID 保留字符串。权限被撤销时清除当前资源消息和草稿；401 清除整个身份。前端状态不是授权依据。
- WS 错误帧当前没有 `msg_id`，同连接并发发送时无法可靠归因。第一批一个连接只允许一个发送中的用户消息；错误/断开时该消息转“待核对”，不把模糊错误附着到其他草稿。若以后需要并发发送，另扩错误帧关联 ID。
- Redis 的 `msg_id` 去重预留只有 5 分钟，不能据此承诺无限期重试一定不会重发。超时先从对应会话历史查同 ID；查不到且已过有效窗口时须明确告知结果不确定，不自动生成新 ID 或静默重发。
- 历史查询和未读查询仍由 IM 按当前身份核权；WS 实时帧只做更新提示，最终以持久查询为准。离线 ACK 与本人显式已读严格分离。
