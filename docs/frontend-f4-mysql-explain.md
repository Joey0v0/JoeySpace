# F4 个人任务查询 MySQL 8.0 执行计划

日期：2026-10-09  
范围：F4-2 `ListMyTasks` 与 `GetTask` 的最终 SQL 形状；仅验证本地合成数据下的执行计划，不代表生产数据分布或线上建索引耗时。

## 验证环境

- MySQL Community Server 8.0.46，Windows x64 便携版，仅监听 `127.0.0.1` 的临时高位端口。
- `tasks` 表字段和既有索引取自当前 `deploy/mysql/init.sql`。
- 插入 100,000 条合成任务，负责人和截止时间分组使用相互独立的序列维度，覆盖 10 个负责人、50 个团队、三种状态以及逾期、七天内、较晚和无截止时间四类数据；被测负责人及团队集合的开放任务四个分组分别有 266、267、533、267 行。执行 `ANALYZE TABLE tasks` 后取 `EXPLAIN FORMAT=JSON`。
- 团队集合查询使用 10 个团队；详情查询使用主键。比较现有索引、候选 A、候选 B，以及 A+B 共存四组结果。

候选索引：

```sql
-- A：覆盖负责人、当前团队集合、状态与截止时间筛选。
(assignee_id, team_id, status, due_at_unix_ms, id)

-- B：优先完成态按 ID 倒序读取。
(assignee_id, status, id, team_id)
```

## 结果

下表的“扫描行”是 `rows_examined_per_scan` 估计值，“成本”是优化器 `query_cost`。开放任务的 `CASE` 分桶仍需 filesort，这是由产品排序规则决定的；索引用于先把排序输入从近五万行缩到约一千三百行。

| 查询 | 现有索引：key / 扫描行 / 成本 / filesort | 仅候选 A | 仅候选 B |
| --- | --- | --- | --- |
| 首屏上界 `MAX(id)` | `idx_tasks_team` / 20,000 / 9002.51 / 否 | `idx_tasks_assignee_team_status_due` / 2,000 / 411.47 / 否 | `idx_tasks_assignee_status_id_team` / 19,310 / 2012.12 / 否 |
| 开放任务首屏 | `PRIMARY` / 49,540 / 9968.50 / 是 | A / 1,333 / 604.86 / 是 | B / 6,667 / 3000.66 / 是 |
| 开放任务续页 | `PRIMARY` / 49,540 / 9968.50 / 是 | A / 1,333 / 604.86 / 是 | B / 6,667 / 3000.66 / 是 |
| 已完成首屏 | `PRIMARY` / 49,540 / 9968.50 / 否 | A / 667 / 302.66 / 是 | B / 3,333 / 1500.11 / 否 |
| 已完成续页 | `PRIMARY` / 49,540 / 4502.51 / 否 | A / 667 / 302.66 / 是 | B / 1,666 / 749.96 / 否 |
| 任务详情 | `PRIMARY` / 1 / 1.00 / 否 | `PRIMARY` / 1 / 1.00 / 否 | `PRIMARY` / 1 / 1.00 / 否 |

A 与 B 同时存在时，六条查询仍全部选择与“仅 A”相同的计划；B 没有被选中。虽然 A 让已完成查询增加一个小结果集排序，但其估计扫描行和成本明显低于 B，并同时显著改善上界与开放任务查询。因此 037 只增加候选 A，不为单一排序再维护第二条复合索引。

## 结论与边界

新增索引：

```sql
INDEX idx_tasks_assignee_team_status_due
    (assignee_id, team_id, status, due_at_unix_ms, id)
```

本次已在真实 MySQL 8.0 上验证最终查询形状和候选索引选择。上线前仍要在目标数据库核对任务量、字段分布、磁盘空间、DDL 算法与锁等待，并在维护窗口执行 037；本地合成数据不能证明生产延迟。
