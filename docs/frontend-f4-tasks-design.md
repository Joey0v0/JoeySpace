# F4 任务与通知设计（用户已确认，2026-10-09）

## 1. 目标与范围

F4 是前端路线的第四个开发阶段，目标是让用户完成“先看讨论，再处理分配给自己的工作”这一段核心流程。本文中的 F12—F16 是架构决定流水编号，不是新的前端阶段。

本阶段交付：

- “我的任务”默认显示当前账号在所有仍有资格的团队中、分配给本人的未完成任务；可以按团队筛选，并单独查看已完成任务。
- 任务详情显示标题、说明、团队、创建者、负责人、状态、截止时间和讨论来源；已创建任务的文字、负责人和截止时间保持只读。
- 用户可以新建任务、更新待办/进行中/完成三态；超时、重复提交和并发变化不造成静默重复或旧状态覆盖。
- 有来源的任务可以回到准确的群消息及邻近上下文，再通过浏览器返回继续处理任务。
- 持久任务通知与任务放在同一个工作区，通过“通知”页签查看并显式标记已读；实时 WebSocket 只提示重新查询。

暂不加入看板拖拽、子任务、评论、附件、优先级、任务文字编辑、批量改状态、日历、提醒规则和通知归档。这些不是当前“讨论 → 本人任务 → 状态 → 来源”闭环的必要条件。

## 2. 调研结论与项目适配

- Linear 的 My Issues 把“分配给我”和“我创建的”分开，默认聚焦真正需要本人处理的事项；Inbox 将通知当成工作提醒，并允许在通知处进入事项继续操作。JoeySpace 首版采用更小范围：默认只有“我负责的”，创建成功后提供任务详情链接，不提前增加订阅、优先级和多套个人视图。
- Linear 把已开始、临期等更需要行动的事项放在前面；Slack Lists 让被分配事项进入 Assigned to you，并把沟通上下文保留在任务旁边。JoeySpace 采用列表和侧面详情，按截止时间组织，不引入看板和任务内新讨论线程。
- 持久通知是事实，实时提醒只是刷新信号。页面收到 `task_notification_changed` 后查询 Task 服务，不能直接用 WebSocket 事件拼任务正文、未读数或状态。

参考：[Linear My issues](https://linear.app/docs/my-issues)、[Linear Inbox](https://linear.app/docs/inbox)、[Slack Lists](https://slack.com/help/articles/27452748828179-Use-lists-in-Slack)。

## 3. 现有能力与缺口

| 需求 | 已有能力 | F4 缺口 |
| --- | --- | --- |
| 查看任务 | 按团队列全部任务，当前团队成员可读 | 没有跨团队“分配给我”、服务端状态/截止时间排序和独立详情 |
| 创建任务 | 团队、标题、说明、负责人、截止时间、来源；幂等键；来源与负责人校验 | Vue 表单、成员选择、同键重试和创建结果恢复 |
| 更新状态 | 创建者、负责人、团队拥有者可改三态；状态与操作/通知同事务 | 没有客户端期望旧状态，并发时旧页面可能覆盖别人的更新 |
| 来源讨论 | 创建时能校验团队群消息；群历史按游标读取 | 没有按目标消息读取邻近上下文，不能可靠定位旧消息 |
| 持久通知 | 当前团队本人通知、分页、逐条显式已读 | 没有跨团队聚合、任务标题/团队名组合及权威未读总数 |
| 实时提示 | 后端已发送最小 `task_notification_changed` 提示 | Vue 的 WS 连接目前属于消息页，任务页还没有连接和共享的新提醒状态 |

现有 `tasks` 索引只有 `(team_id, id)`；正式实现跨团队本人列表前，应为负责人、状态、截止时间和任务 ID 的查询准备新索引。通知已有 `(recipient_id, id)`；若提供全量未读计数，需要在真实 MySQL `EXPLAIN` 后决定是否补 `(recipient_id, read_at, id)`，不在设计稿中先宣称索引已足够。

## 4. 页面结构

“通知也放在任务工作区”沿用已确认方向，左侧模块导航仍只有“消息”和“我的任务”，不再增加第三个常驻模块。

```text
┌────────┬──────────────────┬───────────────────────────────┐
│ 消息   │ 我的任务          │ 任务列表                       │
│ 任务 ● │ ───────────────  │ ┌───────────────────────────┐ │
│        │ [待处理] [已完成] │ │ 临期 · 修复登录失败      > │ │
│        │ [通知 3]          │ │ 工程团队 · 进行中 · 明天    │ │
│        │                  │ ├───────────────────────────┤ │
│        │ 团队              │ │ 无期限 · 补充部署说明     > │ │
│        │ ● 全部团队        │ │ 平台团队 · 待办             │ │
│        │ ○ 工程团队        │ └───────────────────────────┘ │
│        │ ○ 平台团队        │                          [+新建]│
└────────┴──────────────────┴───────────────────────────────┘
                                   选择后从右侧打开详情面板
```

- `/tasks` 默认进入“待处理”，只展示分配给本人且状态为待办/进行中的任务。
- “已完成”单独读取，不让大量历史完成项淹没当前工作。
- “通知”与任务使用同一页面骨架；通知条目包含任务标题、团队、操作者、状态变化、时间和已读状态。
- 团队筛选从已有本人团队目录产生；“全部团队”由服务端聚合，不在浏览器循环请求每个团队。
- 任务详情和新建表单使用页面内右侧面板，桌面宽度约 380—440px，不占满整个浏览器。窄于 1100px 时覆盖在列表上方并提供明确关闭按钮；本阶段仍以电脑浏览器为主。
- 列表行仅放标题、团队、状态、截止时间和来源标记。说明、创建者、完整来源及状态按钮进入详情，避免列表臃肿。

## 5. 主要交互

### 5.1 本人任务

待处理任务按“已逾期 → 未来七天 → 更晚 → 未设置截止时间”分组；组内按截止时间、任务 ID 稳定排序。第一页固定当前时间与任务 ID 上界，后续使用不透明游标；新任务通过刷新进入，状态变更成功后重新读取当前范围。完成任务按最近任务 ID 倒序展示。

空列表明确写“目前没有分配给你的待处理任务”，保留“新建任务”和“查看通知”入口。读取失败保留已加载内容和重试按钮，不显示为任务已处理完。

### 5.2 任务详情与状态

详情使用 `/tasks/teams/:teamId/:taskId` 深链接，刷新时重新核权读取。状态按钮根据当前状态展示合法目标，但最终权限与并发判断由 Task 服务决定。

状态请求同时提交页面读取到的 `expected_status`。服务端发现任务已被别人改变时返回冲突，页面保持服务器状态并提示“任务状态已变化，请重新确认”，不能用旧页面覆盖新结果。请求超时后先重读详情：若已到目标状态则显示成功；仍是旧状态才允许用相同预期再次提交；若变成其他状态则按冲突处理。

### 5.3 新建任务

从任务工作区新建时选择团队、标题、说明、负责人和可选截止时间，来源为空。从团队群某条持久消息选择“创建任务”时预填团队、群和消息 ID，并在表单中显示来源摘要；私聊不作为首版团队任务来源。

负责人从当前团队成员目录选择，可以选择本人、其他成员或“未指派”，不允许手填用户 ID。日期输入按 Asia/Shanghai 展示，提交 UTC Unix 毫秒。

第一次提交生成一个幂等键，并冻结该次规范化请求。超时或结果不确定时保留表单和原键，提供“核对并重试”；在结果明确前不允许修改后换新键，以免第一次已成功却创建重复任务。成功后打开新任务详情；任务若分配给别人，不强行加入“我负责的”列表。

### 5.4 来源定位

点击“查看讨论来源”进入 `/messages/teams/:teamId/groups/:groupId?focus_message_id=:messageId`。IM 在当前权限下返回目标消息及前后邻近消息，页面高亮目标；无权、消息不存在或来源服务暂不可用分别显示明确状态。浏览器返回键回到原任务详情，不接受任意 `returnTo` URL。

从消息创建任务时，仅对已经持久化、有正消息 ID 的团队群消息提供入口。实时消息尚未确认进入历史前不显示该操作。

### 5.5 通知

通知默认未读优先、组内按通知 ID 倒序；点开通知只打开对应任务，不自动标记已读。用户明确点击“标记已读”后才写入首次阅读时间，已读不等于任务完成。

任务工作区的“通知”页签显示 Task 返回的权威未读数；左侧模块导航只显示“存在未读或可能有更新”的圆点，避免在未查询时伪造全局数字。收到实时提示时显示圆点并在任务页触发一次串行刷新，刷新成功后采用权威未读数。重复 notification ID 合并；断线重连重新读取第一页。临时失败保留提示点和现有通知，不猜测新内容。

## 6. 推荐接口与责任边界

### F12：Task 持有跨团队本人任务读模型（用户已确认）

新增 `Task.ListMyTasks` 和 `Task.GetTask`，由 Bearer metadata 得到本人，不接受客户端传 `user_id`。`ListMyTasks` 支持待处理/已完成、可选单团队和游标分页，返回 `team_id` 及现有任务字段；`GetTask` 支持深链接恢复，并返回由服务端权限规则计算的 `can_update_status`。Task 先按本人关系查询，再复核每个返回团队的当前资格。

Gateway 暴露 `GET /api/v1/tasks` 和 `GET /api/v1/teams/{team_id}/tasks/{task_id}`，使用 User 补团队名与有限显示名。浏览器不遍历团队，也不把当前页过滤结果称为完整“我的任务”。原按团队任务列表继续保留，供后续团队任务页面复用。

备选是在 Vue 中逐团队读取现有列表并筛负责人。改动少，但请求数随团队增长、每个团队仍需翻完全部任务才能知道本人范围，排序和分页会漏项，因此不采用。

### F13：状态变更加旧状态前提（用户已确认）

`SetTaskStatus` 增加 `expected_status`，Task 在现有行锁事务内比较；不一致返回 `Aborted`，Gateway 映射 HTTP 409。无需新表或版本列。原同状态重试仍为幂等成功。

备选保持无条件覆盖，前端仅在超时后重新查询。它仍可能在“查询后、重试前”覆盖同事刚完成的状态，不符合协作页面的可预期性，因此不采用。

### F14：Task 持有跨团队本人通知聚合（用户已确认）

新增 `Task.ListMyTaskNotifications`，只返回本人仍有团队资格的通知，包含 `team_id`、任务标题、当前状态和现有通知字段，并返回权威 `unread_count`。Gateway 补团队名与操作者显示名。逐条已读继续复用团队范围写入口，不改变通知数据归属。

备选首版只做当前团队通知。后端已有能力，但用户必须切换团队才能发现其他工作，与“我的任务”跨团队入口不一致；因此建议 F4 一次补齐个人聚合。

### F15：IM 提供有权限的来源上下文（用户已确认）

新增按 `team_id/group_id/message_id` 读取目标及邻近消息的 IM RPC/Gateway GET。复用群历史的当前团队与群成员资格、关闭代际和提及关系读取；目标不存在与无权均不泄露其他群信息。响应有固定小上限，不从浏览器循环“加载更早”直到碰到目标。

备选只打开群聊最新页并显示来源消息 ID，不能真正定位讨论；另一个备选由浏览器无限翻页，慢且可能永远找不到，均不满足来源回跳。

### F16：路由内复用实时客户端并共享通知信号（用户已确认）

扩展现有 Vue WS 客户端严格解析 `task_notification_changed`。消息页和任务页各自在当前路由内持有一个客户端：切换模块时先销毁旧连接，再由新页面重新签票连接，因此同一时刻仍只有一个浏览器连接。两页通过一个只保存“通知可能有更新”的轻量响应式模块驱动导航圆点；任务页收到提示或重连后查询权威通知。退出或身份变化清除该信号和任务/通知缓存，不因这一项引入 Pinia。

备选把聊天发送、消息订阅和通知全部提升到 App 级单例，连接切换更少，但会扩大 F3 已验证发送/重连状态的重构范围。首版采用路由内连接，代价是消息与任务模块切换时会重新签票和连接；持久通知与进入页面后的权威查询保证不会丢事实。

## 7. 数据库与部署影响

- 预计新增 037 迁移，为跨团队本人待办查询增加组合索引；通知未读索引是否同批增加，以真实 MySQL 8.0 `EXPLAIN` 为准。
- 不新增服务、语言、中间件或前端组件库。Task 继续拥有任务/通知，IM 继续拥有消息和来源访问，User 继续拥有身份/团队/成员资料，Gateway 只组合当前页读模型。
- F4 前端继续使用 TypeScript + Vue 3 + Vite、Vue Router 和现有 API 客户端；列表、面板和表单用项目样式实现，暂不引入大型表格或 UI 框架。
- 新接口上线前先执行迁移；旧按团队接口和原生演示页保持兼容。完整部署与真实双账号浏览器验收仍放到 F6，但 F4 本地批次需做实际 HTTP→gRPC 组合和浏览器替身验证。

## 8. 验收标准

- 两个团队中只有真正分配给本人的未完成任务进入默认列表，跨页不漏、不重复，退出团队后不再返回。
- 大整数 ID 全程为字符串；账号、筛选或路由变化后，旧请求不能污染新页面。
- 创建超时使用同一幂等键核对；状态并发冲突不会覆盖新状态。
- 任务深链接刷新可恢复；来源跳转准确高亮目标消息，无权时不泄露正文。
- 通知跨团队聚合、逐条已读和权威未读数一致；收到 WS 提示或重连后查询持久事实。
- 1280、1440、1920 宽桌面浏览器中列表与侧面板可用，无横向溢出；键盘焦点、表单标签、状态不能只靠颜色区分。

## 9. 用户确认结论

用户已确认同时采用 F12—F16。它们都服务于既定 F4，不改变 Task/IM/User 的数据归属；主要代价是新增 Task 两类本人聚合读接口、一个任务详情、一个 IM 来源上下文接口、状态前提字段和可能的 037 索引迁移。确认后按独立实施计划开发，不在本设计提交中提前写业务代码。
