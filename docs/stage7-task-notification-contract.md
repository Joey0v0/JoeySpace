# 阶段7第一步：任务状态通知持久化契约

日期：2026-10-05。范围仅是 Task 服务在真实状态变更时保存个人通知依据，不开放查询、已读或实时推送；第一版个人入口及数据归属见[架构记录](architecture-decisions.md) A65/A66。

1. `SetTaskStatus` 仍先核对操作者当前团队资格及原有创建者/负责人/团队拥有者修改权限。按任务 ID 和团队 ID 锁定任务；状态与当前状态相同时直接成功，不新增操作或通知。
2. 真实变化仍在同一 MySQL 事务中更新 `tasks.status`、插入一条 `task_operations`，然后按创建者、当前负责人去重插入 `task_status_notifications`。负责人为空或与创建者相同则只插一条；操作者若也是接收人，本步仍保留其个人通知，以符合已选的两类接收人范围。
3. 通知行包含唯一的 `(operation_id, recipient_id)`、团队/任务 ID 与创建时间；读取时可通过操作 ID 获得行为人和原/新状态。任何通知写入失败须回滚任务状态和操作记录；RPC 不能报告成功。不得在事务前发送 Kafka、WebSocket 或 HTTP。
4. 已有数据库先核对 `007_task_operations.sql`，再执行一次 `027_task_status_notifications.sql`；新数据库的 `deploy/mysql/init.sql` 与迁移定义相同。本轮只做 SQL 替身与服务测试，不执行真实迁移。

后续本人查询必须从身份与当前团队资格出发，并验证只读自己的通知；记录落库不代表已读、在线送达或群内回帖。通知的读取分页、已读语义及实时通路分别作为后续小步设计。
